# RakNet: датаграммы и пакеты

Как бот общается с сервером на уровне RakNet.
Код: `core/network.py` (отправка байт) и `core/protocol.py` (разбор/сборка).
Побитовые чтения/записи — в [`BITSTREAM.md`](BITSTREAM.md).

## Два уровня: не путай

1. **UDP-датаграмма** — то, что реально летит по сети. Один `send()` = одна датаграмма.
2. **Пакет** — в одной датаграмме их может быть несколько подряд, у каждого свой заголовок и тело.
3. **Тело пакета** — байты SA-MP (RPC, sync и т.д.). Этот документ их не разбирает.

```
UDP-датаграмма
└── [ACK-блок?] + [пакет1][пакет2][пакет3]...
                    └── заголовок + тело (байты SA-MP)
```

`core/network.py` работает только с датаграммами: `send()` отправить, `recv()` прочитать. `core/protocol.py` разбирает датаграммы на пакеты и собирает их обратно.

## Структура датаграммы

```
[ has_acks : 1 бит ]
[ ACK-блоки — только если has_acks = 1 ]
[ пакет1 ][ пакет2 ]... — пока не кончатся байты
```

* `has_acks` — флаг: "в начале датаграммы лежат подтверждения".
* Если датаграмма состоит только из подтверждений и пакетов в ней нет — это чистая ACK-датаграмма.
* ACK-блоки — это список диапазонов номеров (подробнее ниже в разделе про подтверждения).

## Структура одного пакета

Поля идут строго по порядку, бит за битом:

```
1. message_number   : 16 бит (uint16)
2. reliability      : 4 бита
3. ordering_channel : 5 бит  — только если reliability = 7, 9, 10
   ordering_index   : 16 бит — только если reliability = 7, 9, 10
4. has_split        : 1 бит
   split_id         : 16 бит — только если has_split = 1
   split_index      : сжатое uint32 — только если has_split = 1
   split_count      : сжатое uint32 — только если has_split = 1
5. bitlen           : сжатое uint16 (длина тела в БИТАХ)
   выравнивание до целого байта
6. тело пакета             : (bitlen + 7) // 8 байт
```

Нюанс сборки: первая запись в датаграмме пишется с `has_acks` в начале (полный заголовок), остальные — без него (короткий заголовок). При разборе `has_acks` читается один раз в самом начале датаграммы.

## Что значит каждое поле

### has_acks — 1 бит

Флаг "датаграмма начинается с подтверждений".

Подтверждения (ACK) идут сразу после `has_acks`, до первого пакета. Формат: количество диапазонов (сжатое число), дальше для каждого диапазона флаг "один номер или отрезок" + сами номера `uint16`.

Пример: сервер подтверждает пакеты 10, 11, 12 и 20 — это упакуется как два диапазона `[10-12], [20-20]`, а не 4 отдельных числа.

### message_number — 16 бит

Порядковый номер пакета. Выдаётся по кругу от 0 до 65535.

Зачем нужен:

* бот понимает, какие его пакеты дошли, а какие надо переотправить;
* получатель понимает, что это дубликат (номер уже встречался) и его надо выкинуть;
* по номерам из ACK бот чистит очередь повторов и замеряет пинг.

Номер есть у всех пакетов, даже у ненадёжных. Разница в том, что ненадёжные по нему не подтверждаются и не переотправляются.

### reliability — 4 бита

Тип доставки пакета. Число от 6 до 10 (см. `PacketReliability` в `samp/constants.py`).

| Значение | Название | Простыми словами |
|---|---|---|
| 6 | `UNRELIABLE` | Отправил и забыл. Может потеряться, может прийти дважды. Подтверждений и повторов нет. |
| 7 | `UNRELIABLE_SEQUENCED` | Без повторов, но доходит только самое свежее. Старые пакеты канала выкидываются. |
| 8 | `RELIABLE` | Точно дойдёт (повторяется, пока не подтвердят). Но порядок не гарантируется. |
| 9 | `RELIABLE_ORDERED` | Точно дойдёт и строго по порядку. Опоздавшие ждут своей очереди. |
| 10 | `RELIABLE_SEQUENCED` | Точно дойдёт, но из очереди берётся только самое свежее. Старое выкидывается. |

SA-MP в основном пользуется надёжными типами. Ненадёжные — для частых обновлений, где потеря одного пакета не страшна (пакеты синхры и т.п.).

### ordering_channel (5 бит) + ordering_index (16 бит)

Есть только у типов 7, 9, 10. У типов 6 и 8 этих полей нет вообще.

* `ordering_channel` — номер канала (0..31). Потоки не мешают друг другу: порядок считается отдельно в каждом канале.
* `ordering_index` — номер пакета внутри канала. По нему получатель решает: отдать сразу, придержать (для ORDERED) или выкинуть как устаревший (для SEQUENCED).

### has_split + split_id / split_index / split_count

Флаг "пакет разрезан на куски".

Лимит одной датаграммы — 576 байт. Если пакет с заголовком не влезает, он режется на фрагменты с общим `split_id`. У каждого фрагмента свой `split_index` (0, 1, 2...) и общее `split_count`.

Получатель копит фрагменты, когда собраны все — склеивает их в целый пакет. Несобранные через 30 секунд выкидываются.

### bitlen + body

`bitlen` — длина тела в битах (сжатое число). Дальше поток выравнивается до целого байта и читается тело: `(bitlen + 7) // 8` байт.

Тело — это уже данные SA-MP. RakNet про их содержимое ничего не знает.

## Подтверждения (ACK)

Когда отправитель пакета получает надёжный пакет (типы 8, 9, 10), он запоминает его номер как "надо подтвердить". Подтверждения не уходят по одному — они копятся и периодически отправляются одной ACK-датаграммой со списком диапазонов.

В обратную сторону так же: когда сервер присылает ACK, отправитель пакета удаляет эти номера из очереди повторов. Что не подтверждено дольше ~2 секунд — отправляется заново.

По этому же времени считается пинг: отправил надёжный пакет — дождался его ACK.

## Приём: дубликаты, порядок, склейка

Каждый разобранный пакет проходит по цепочке:

1. Надёжный? Запомнить номер для исходящего ACK.
2. Такой номер уже встречался? Выкинуть как дубликат.
3. Это фрагмент разрезанного пакета? Отложить, если собраны все — склеить.
4. Применить правило порядка: `RELIABLE_ORDERED` ждёт своей очереди, sequenced-типы пропускают только свежее, остальные отдаются сразу.
5. Готовые пакеты складываются в очередь приёма, откуда их забирает `recv_and_parse()`.

## Отправка

1. Байты SA-MP оборачиваются в заголовок пакета: выдаётся новый `message_number`, пишется `reliability`, при необходимости ordering-поля, `has_split`, `bitlen`.
2. Если не влезает в 576 байт — режется на фрагменты.
3. Пакеты копятся в очередях по приоритетам. `update()` собирает их в датаграммы: первый с полным заголовком, остальные с коротким, пока влезают в лимит.
4. Готовая датаграмма шифруется `samp_encrypt()` и уходит в `network.send()`.
5. Надёжные пакеты лежат в очереди повторов, пока сервер не подтвердит их ACK-ом.

## Шифрование

Шифруется только исходящий трафик (бот -> сервер).

Входящие датаграммы не расшифровываются: сервер шлёт открытым текстом, поэтому `parse_datagram()` работает сразу с байтами из `network.recv()`. Функции `samp_encrypt()` / `samp_decrypt()` лежат в `core/security.py`.

## Пакеты без заголовка

`send_raw()` шлёт байты как есть, без заголовка пакета (но с шифрованием). Так отправляются handshake-пакеты — запрос соединения и подобные, которые идут до установки соединения.
